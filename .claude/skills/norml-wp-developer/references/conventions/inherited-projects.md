# Inherited Projects — Working Inside an Existing Theme

This document defines how to work inside a WordPress project you didn't scaffold — a theme inherited from a client, a previous agency, or an in-house developer. These are typically vanilla WordPress, a custom theme, Understrap, GeneratePress, a Genesis child theme, a Bootstrap-based starter, or anything else.

**Read this file FIRST whenever you open a WordPress project you didn't build yourself.**

The other files in this skill (`references/dev-conventions.md` Mode A, `references/conventions/css-architecture.md`, `references/conventions/acf-blocks.md`) describe how to build new themes from scratch. This file describes how to apply the core principles inside someone else's existing structure without rewriting the world.

---

## The default: respect the existing architecture

Opening an inherited theme is not an invitation to modernize it. Your first job is to understand it, then extend it on its own terms.

**Don't introduce a new framework, build system, or templating engine without explicit approval.** Don't add Sage. Don't add Acorn. Don't add Blade. Don't replace the existing CSS pipeline. Don't add Tailwind v4. Don't add Alpine.js unless the theme already uses it. Each of those is a multi-day refactor that ripples through every other file — they belong to a planned scope, not a "while I was in there" addition.

---

## Read the theme first — the mapping checklist

Before writing a single line of new code, spend 15 minutes mapping what already exists. Run through this checklist and report back a one-paragraph summary to the user.

| Area | What to identify |
|---|---|
| **Entry point** | `functions.php`, `inc/`, `lib/`, `includes/`, or custom hook loader |
| **Template hierarchy** | Which of `single-{cpt}.php`, `archive-{cpt}.php`, `page-{slug}.php`, `page-{template}.php` are present |
| **Section / component organization** | `template-parts/`, `partials/`, `parts/`, `components/`, `blocks/`, or none |
| **Asset pipeline** | Webpack, Vite, Gulp, Laravel Mix, plain CSS/JS, or none |
| **CPT / taxonomy registration** | PHP code in theme, CPT UI plugin, ACF PRO JSON, or a custom plugin |
| **ACF usage style** | PHP-registered field groups, local JSON sync, synced from admin only, or not used at all |
| **Block registration** | Native `block.json`, ACF blocks via `acf_register_block_type()`, both, or a page builder instead |
| **Page builder** | Elementor, Divi, WPBakery, Beaver Builder, Bricks, Oxygen, native Gutenberg, or classic editor |

If `{theme_root}/.claude/docs/` already exists — generated by this skill's init flow — read it first. The architecture map is already there. If it doesn't exist, run the init flow in scrape mode before starting any non-trivial work.

**Match the existing patterns when you add new code.** If the theme keeps sections under `template-parts/sections/`, your new section goes there — not in a freshly invented directory. If it uses `get_template_part()` for includes, use that — don't bolt a foreign templating system onto a vanilla PHP theme. If field group keys look like `group_5fc83e1234567`, don't suddenly start writing `group_descriptive_name`. Consistency beats your preference.

## Core principles — framework-agnostic

These apply inside any inherited theme. They are tooling-agnostic. Sage just makes them ergonomic — the principles themselves are not Sage-specific.

### 1. Sections / components / partials separation

Whatever the theme calls them, three layers should exist:

| Layer | What it is | Typical non-Sage location |
|---|---|---|
| **Sections** | Full-width page blocks — hero, benefits, FAQ, CTA. One file per section. | `template-parts/sections/`, `partials/sections/`, `parts/sections/`, `blocks/` |
| **Components** | Small reusable UI atoms — button, card, icon, modal. One file per component. | `template-parts/components/`, `parts/components/`, `components/` |
| **Partials** | WordPress loop fragments — `content.php`, `content-single.php`, `content-page.php`. | Root of `template-parts/` |

If the inherited theme doesn't separate these — everything dumped at the theme root, or one giant `template-parts/` with no sub-folders — **add the missing folder rather than continuing the mess.** Match the theme's existing naming convention: if it uses `parts/` instead of `template-parts/`, use `parts/`.

One file = one section. No 500-line `page.php` or `front-page.php` with everything inline.

### 2. Sections fetch their own ACF data; components receive props

A **section** is responsible for getting its own ACF data and rendering. A **component** is stateless — it takes data via arguments and renders. This rule is framework-agnostic.

In vanilla PHP (`get_template_part()` style — the norm in inherited themes):

```php
<?php
// template-parts/sections/benefits.php
// This section owns its own data fetching.
$items = get_field('items') ?: [];
foreach ($items as $item) {
    get_template_part('template-parts/components/card', null, [
        'title'       => $item['title'],
        'description' => $item['description'],
    ]);
}
```

The component reads its props from `$args` (WordPress 5.5+):

```php
<?php
// template-parts/components/card.php
// This component is stateless — it never calls get_field().
$title       = $args['title'] ?? '';
$description = $args['description'] ?? '';
?>
<div class="card">
    <h3><?= esc_html($title); ?></h3>
    <p><?= esc_html($description); ?></p>
</div>
```

The separation of concerns is the rule — the syntax is just the vehicle.

- A component **must never** call `get_field()` directly.
- A section **must never** hardcode markup that belongs in a component.
- A partial (loop fragment) renders individual post items; it doesn't fetch section-level ACF fields.

### 3. Gutenberg + ACF for content authoring — compatibility decisions

The preferred approach for editor-facing content is **Gutenberg as the editor + ACF blocks as the building blocks**. This holds for new pages, new CPT singles, and new CPT archives. But inherited projects have existing editor setups — match them before introducing anything new.

| Inherited setup | What to do |
|---|---|
| Native Gutenberg + ACF PRO already in use | Continue the existing pattern. Add new ACF blocks for new sections. |
| Native Gutenberg without ACF | Keep registering native blocks via `block.json`. Don't force ACF in. |
| ACF without proper block registration (page-level fields + empty `the_content()`) | Most common refactor candidate. Surface it: propose migrating page-level ACF to ACF blocks so editors can rearrange sections. Wait for approval. |
| Elementor / Divi / WPBakery / Beaver Builder / Bricks / Oxygen | **Do NOT silently introduce Gutenberg as a parallel system.** Either stay inside the existing builder for the task, or surface the trade-off and plan a migration as a separate scope. |
| Classic editor with shortcodes everywhere | Surface. Almost always worth a migration plan. Don't add new shortcodes. |

### 4. ACF block registration pattern

See `acf-blocks.md` for the full canonical registration pattern — the guard, the category filter, the `render_callback` vs `render_template` choice, block previews, and field group key conventions. That file is the single home for ACF block code.

The short version for inherited themes: register inside `acf/init`, guard with `function_exists('acf_register_block_type')`, give every block a dedicated template file, declare a block category, support `anchor`, and provide a preview in the inserter. Never inline render markup in the registration array.

### 5. CPT + archive + single = blocks-based by default

When adding a new custom post type with both archive and single views:

**Single template** (`single-{cpt}.php`):
- Render `the_content()` so the editor controls the body via Gutenberg blocks.
- Hardcode only the truly fixed chrome — hero with title/meta, related-posts at the bottom, share buttons.
- Wrap variable chrome in ACF blocks whenever the layout might differ across posts in the same CPT (e.g., some case studies have a video hero, others have an image hero).

**Archive template** (`archive-{cpt}.php`):
- The surrounding page (intro section, filters, CTA) is built from ACF blocks placed on the CPT archive's editable surface — either an ACF options-style group bound to the archive URL, or a real page whose slug matches the CPT archive URL with a `template_redirect` to render its blocks above the loop.
- The actual loop renders item cards using a reusable card component.

**The test:** the editor should never have to ask a developer to change the hero copy on the blog index page, or to reorder sections on a case study page. If the architecture forces that, it's wrong — surface it.

### 6. WordPress hook discipline

Hooks belong in dedicated files, not scattered through templates. A `functions.php` that is 2,000 lines of `add_action()` calls is a code smell.

Group hooks by concern. Common structure for inherited themes:

```
inc/
├── blocks.php      ACF block registration, block category filter
├── cpts.php        register_post_type(), register_taxonomy()
├── enqueue.php     wp_enqueue_scripts, enqueue_block_editor_assets
└── cleanup.php     remove_action() calls, admin bar, emoji script removal
```

When you're adding code to a theme that doesn't yet have this separation: create the file for your concern, `require_once` it from `functions.php`, and leave a comment explaining the pattern so the next developer understands it was intentional.

### 7. CSS architecture

Apply the 3-layer CSS model inside the inherited theme — see `css-architecture.md`. The short rule: design tokens at `:root`, shared components in a single always-loaded stylesheet, per-block layout in conditionally-enqueued per-block files. No per-page stylesheets, ever.

When introducing the model on an inherited project: apply it one new block at a time. Don't refactor existing blocks without approval.

## Decision flow when starting work

```
1. Read the theme top-to-bottom
   (functions.php → inc/lib/includes → template-parts → assets → acf-json or PHP fields)

2. Identify:
   - Framework / templating engine
   - Build system (or none)
   - ACF usage style
   - Block registration approach
   - CPT / taxonomy registration approach
   - Page builder, if any

3. Document what you found (one-paragraph summary to the user)

4. For the requested task:
   ├── Does the existing pattern support it cleanly?
   │   └── YES → follow the existing pattern.
   │            Apply the core principles inside it.
   │
   └── NO → propose a refactor as a separate scope.
            ├── If user approves refactor →
            │     do it as its own task with its own changelog entry.
            └── If user defers →
                  match the existing (suboptimal) pattern for now.
                  note the tech-debt in {theme_root}/.claude/CLAUDE.md.
```

## What you MAY introduce silently

These fill obvious gaps without restructuring anything. No approval needed:

- A new section file under the theme's existing section folder
- A new component file under the theme's existing component folder
- A new ACF block registration in the theme's existing block-registration file
- A new ACF field group (saved wherever the theme has ACF JSON configured, or via PHP if that is the existing pattern)
- A new partial under the theme's existing partial folder
- A new utility class in the theme's existing shared CSS file
- A new icon under the theme's existing icon folder or sprite
- An `inc/{concern}.php` file when `functions.php` clearly needs the relief and the file only moves existing-pattern code to a dedicated home

---

## What you MUST NOT introduce silently

These restructure the project and have multi-day downstream effects. Surface each as a proposal, wait for explicit approval, then do it as its own scope with its own changelog entry:

- A new framework or templating engine (Sage, Blade, Twig, Timber)
- A new build pipeline (Vite, Webpack rewire, esbuild, Gulp replacement)
- A new CSS framework (Tailwind v4, Bootstrap replacement)
- A new JS framework (Alpine.js, React, Vue) if the theme doesn't already use it
- A new global folder structure (`resources/`, `src/`)
- Replacing PHP-registered ACF fields with JSON sync (changes the workflow for the whole team)
- Replacing native Gutenberg blocks with ACF blocks, or vice versa
- Replacing CPT UI plugin registration with code-registered CPTs, or vice versa
- Removing or replacing a page builder (Elementor, Divi, WPBakery, Bricks, Oxygen)
- Renaming or moving the theme's `template-parts/`, `parts/`, or `components/` folder

## Surfacing refactor candidates

If the existing architecture is genuinely problematic and worth changing, say so explicitly. Don't silently work around it. Say:

> "This theme's section organization is going to be hard to extend safely. We can keep matching the existing pattern, or we can refactor `X` to `{Y}`. Refactor would touch approximately `Z` files and unblock `{benefit}`. Want me to plan it as a separate ticket?"

Then **wait for the user's decision.** Never refactor silently while doing something else.

Common patterns worth surfacing:

- Templates with thousands of lines of inline HTML and no partial extraction
- ACF fields hard-coded in PHP that should be JSON-synced for diffability and team portability
- jQuery soup with no module boundaries and broken interactivity on mobile
- "Blocks" rendered via huge `the_content()` filters or shortcodes instead of proper block registration
- Page builder lock-in that makes content unportable and cannot be exported to block markup
- No design tokens — every color is a hex literal in 200 places across 15 files

## When refactoring IS the task

If the user explicitly asks to refactor the inherited theme — "let's migrate this Elementor site to Gutenberg", "let's pull these PHP-registered ACF fields into JSON sync", "let's split this monolithic functions.php" — then refactor freely within the agreed scope.

Even then, do it in phases:

**Phase 0 — snapshot.** Full DB + files backup. Document the rollback path. No code change in this phase — if you can't roll back cleanly, you can't start.

**Phase 1 — parity.** Rebuild the existing structure in the target pattern. Don't change behavior yet. At the end of Phase 1, the site should look and behave identically to before — only the code organization differs.

**Phase 2 — cutover.** Switch the theme, page, or post type to the new structure. Run QA gates per `../qa-gates.md` before marking done.

**Phase 3 — cleanup.** Remove the old structure. Drop dead code. Update any project documentation under `{theme_root}/.claude/`.

Rules:

- Each phase is its own PR with its own changelog entry.
- Never bundle a refactor into a feature PR.
- If Phase 1 reveals the parity cost is higher than estimated, surface it before proceeding to Phase 2.
