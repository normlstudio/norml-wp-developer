The problem

You're building a WordPress theme and you want the developer-friendly flow — work locally, commit, push, watch CI/CD deploy to staging, smoke test, promote to prod. But wiring that up by hand is half a day of yak-shaving: Git remote, GitHub auth, SSH keys, GitHub Actions YAML, local WP config. And maintaining it across a dozen client projects is its own tax.

This skill makes the per-project setup about 30 minutes, then turns the everyday workflow basically chat-driven: build a block, ship to staging, promote to prod. Every production write stops for an explicit backup acknowledgement — there's no autopilot over your live site.

After setup, each project carries its own committed `.claude/` folder, so the next session — you, a teammate, or Claude — starts with full context: the CI/CD pattern in play, the conventions to follow (Sage or inherited), and the recent changelog.

Backups are on you
This skill does not make backups. Every production write — rsync, `wp db import`, `wp search-replace` — refuses to run without an explicit "I have a backup" acknowledgement. It assumes your host has automatic backups on, or that you take manual ones before destructive ops. If you lose data, no skill can recover it.
What it does

It works in two modes — a new Sage build, or an inherited non-Sage theme it respects rather than rewrites. Setup is ~30 min per project; everyday work is chat-driven.

What it won't do
Make or restore backups — every prod write gates on a backup you confirm; it never creates one.
Manage content or ACF values on a live site — that's the companion, `norml-wp-manager` (REST, no SSH).
Introduce a new framework on an inherited theme without asking — it matches what's already there.
Fix a broken WordPress install — corrupted database or core files go to your host.
Security or penetration testing — out of scope; use a dedicated tool.

Local-first is the default. Direct-on-server edits are permitted but flagged `[DIRECT-PROD]` and logged, because the next deploy can overwrite them.
